## 0. Summary

1. **The 4th problem is real and the docs confirm it.** After `/clear`, `/resume` or `/branch` the engine runs on under a **new session id**, `session.start` does **not** fire again, and `$.state` resets (mods reference, Session table; types `SessionEndInput`). `register.tsx` learns the id once at `session.start` (`register.tsx:147`, `:304`). So after such a command it keeps writing figures under the **old** id. The desktop moves the old id into `priorCliSessionIds` [code]. The sanctioned fix is a `classic.SessionStart` hook with `source` `clear`, `resume` or `fork` (mods "Draw in the interface" page, section "Load a saved value again after `/clear`"), or reading `$.session.id()` at every publish.
2. **Issue #2 (Context line missing in a session), hypothesis A (the mod is not loaded there).** The docs confirm the general rule: a running session keeps the plugin set it loaded at startup or at its last `/reload-plugins`. The documented remedy in a desktop session is to **type** `/reload-plugins` in that session's prompt box. It is refused when it arrives over Remote Control. A changelog note (2.1.274) and the app's code (`installedPluginsWatcher`, `broadcastReloadPlugins`, behind a feature flag) show that Desktop can reload open sessions' plugins by itself when `installed_plugins.json` changes. That covers the 12:03Z marketplace install, but not the morning `CLAUDE_CODE_PLUGIN_DIRS` route.
3. **Issue #2, hypothesis B (no store record).** No official page documents `%APPDATA%\Claude\claude-code-sessions` at all, so the docs can neither confirm nor contradict B. Local data contradicts the "Remote Control" part: 798 of 993 records carry `bridgeSessionIds`, so sessions with Remote Control on do get records [local]. Issue #2's own facts do not reproduce on `MSI`: 993 records here, not 2108; no record `68ec5dbf`; other figures-file ids. It was probably observed elsewhere [local, inference].
4. **Issue #3 (Context line shows the previous session's figures while a new session is starting).** The docs say a fresh session has **no** context figures until its first response (`tokens` and `percent` absent). Showing another session's figures is therefore never right. Chromium names the UIA `Document` after `document.title` and raises a Name-changed event when it changes [code]. So the title is readable at any moment, but what the app puts there during "Starting session" is undocumented and needs a capture.
5. **The sanctioned way to draw a per-session context line in the desktop app is the mod itself.** The docs list `SessionMode` (the footer's mode-label slot) and `AbovePrompt` as render sites on **Terminal and Desktop**. The mod already has `/ctxbar footer` and `/ctxbar top`. Drawing in the app removes the title-to-record-to-id mapping that issues #2, #3 and the 4th problem all depend on.
6. **Undocumented contracts the overlay relies on:** the desktop session store and every field it reads; the page title format "`<title> - Claude Code`"; the accessible names "Environment: …", "Add another folder", "worktree", "Model: …"; the `folder=` parameter of `claude://code/new`. The docs only list `ssh_host`, `ssh_port`, `ssh_folder` and `q`. Chromium exposes a DOM `id` as the UIA `AutomationId` [code], which would be a sturdier anchor than localized names if the app sets ids (unverified).
7. **Issue #1 (Button hidden on the new-session screen when no folder is selected):** nothing official covers the new-session screen's accessibility tree. No mod can draw there, because no session runs yet. The fix stays an overlay heuristic; see section 2.

## 1. Mechanism facts

### 1.1 Session id lifecycle

- **What `$.session.id()` is.** "Returns the session's id (the transcript file's name)" [read: skill `types/claude-code.d.ts:2794`]. Transcripts live at `~/.claude/projects/<project>/<session-id>.jsonl` [read: docs `sessions` page, "Where transcripts are stored"].
- **`session.start` fires once per loaded mod, then again only on a reload of that mod.** The mods reference says: "Once for each loaded mod, before the first prompt, and again after a reload of that mod. Not after `/clear`, `/resume`, or `/branch`." [read: https://code.claude.com/docs/en/plugins/mods/reference, Session table, line 136 of the raw page]. The types say the same: "Fires once per process for each loaded plugin, before the first prompt, then once per fresh load of one (never `/clear`)" [read: types `:4324`].
- **`/clear`, `/resume` and `/branch` change the id inside one process.** `SessionEndInput.reason`: "`clear` is how a hook sees a `/clear`: the conversation ends, the process goes on under a new session id, and no `session.start` fires for it". `sessionId`: "after a `/clear` or a resume the process goes on under another" [read: types `:11049`–`:11075`]. The mods reference adds "`/branch` reports `resume`" for `session.end` [read: mods reference line 137].
- **Mod state resets on those commands.** "Each of those commands resets `$.state` to its defaults, and `session.start` doesn't fire again." [read: https://code.claude.com/docs/en/plugins/mods/troubleshoot, "A value resets after `/clear`, `/resume`, or `/branch`"].
- **The sanctioned way to follow the change.** "`classic.SessionStart` does fire after each of them, with `e.source` set to `clear`, `resume`, or `fork`." The docs show `on('classic.SessionStart', { source: ['clear', 'resume', 'fork'] }, …)`, and note that it also fires at startup and after compaction, "which doesn't reset `$.state`" [read: https://code.claude.com/docs/en/plugins/mods/interface, "Load a saved value again after `/clear`"].
- **Inside a `classic.*` hook, `e` is the settings hook's stdin JSON.** That includes `session_id`, `transcript_path` and `cwd` [read: types `ClassicEventOf` `:1238`–`:1252`, `BaseHookInput` `:826`; docs mods "React to events", section "Handle the settings hook events"].
- **SessionStart `source` values.** `startup`, `resume`, `clear`, `compact`, `fork` [read: https://code.claude.com/docs/en/hooks, "SessionStart input"; types `SessionStartHookInput` `:11643`].
- **Compaction.** It raises `SessionStart` with `source: "compact"`. `SessionEnd` has no compaction reason (`clear`, `resume`, `logout`, `prompt_input_exit`, `other`) [read: hooks page "SessionEnd"; types `ExitReason` `:4809`]. So compaction keeps the id [inference]. After compaction the context figures are absent until the next response [read: types `SessionContextUsage` doc `:10943`; statusline page, "current_usage … null … again after `/compact`"].
- **The environment variable follows the id.** `CLAUDE_CODE_SESSION_ID` is set in Bash, hook and MCP subprocesses, "matches the `session_id` field in the hook JSON input and is updated on `/clear`". With `--continue`, or `--resume` without an id, "it may receive the initial startup ID instead" [read: https://code.claude.com/docs/en/env-vars, `CLAUDE_CODE_SESSION_ID`]. That means a process can hold a startup id that differs from the conversation it resumes [inference].
- **`/branch` and `--fork-session` create new ids.** "Sessions created with `/branch` or `--fork-session` get their own session IDs" [read: sessions page, "Use the session picker"].
- **`startedAt` restarts on `/clear`.** `SessionUsage.startedAt` restarts at `/clear` and counts from the first launch for a resumed session [read: types `:11704`–`:11716`].
- **Desktop side, which the docs do not cover.** The app's code has a "Clearing session" path that calls `recordPriorCliSessionId(l, l.cliSessionId ?? l.unarchivedCliSessionId)` and keeps `preClearCliSessionId`. Rewind does the same. Record fields the code knows but that no local record holds today: `preClearCliSessionId`, `unarchivedCliSessionId`, `priorRemoteCliSessionIds`, `historyOnlyCliSessionId` [code: `app.asar` of 2.37337.1].
- **Local data.** 4 of 993 records have non-empty `priorCliSessionIds` (lengths 1, 1, 1, 2), all created 2026-09-10. None of them has a figures file under a prior id [local].

### 1.2 Session title

- **No title in the mod API.** The `$.session` noun has `messages`, `cwd`, `root`, `model`, `turns`, `id`, `repo`, `surfaces`, `usage`, `version`, `compact`, `send`, `append`, `authorize`, and no title [read: mods reference, "Mods API methods" row `$.session`; types `:2738`–`:2900`]. There is no `session.title` event. The render props carry the title only where another session sent a message: `UserMessage.from.name` is "another session's title" [read: types `:14605`].
- **The custom title is reachable through a classic hook.** `SessionStart` and `UserPromptSubmit` hooks receive `session_title`: "The session's custom title, present when one is set, for example with `--name`, `/rename`, a hook's `sessionTitle` output, or the Agent SDK's `renameSession()`". And: "A session you haven't named can still have a generated title. That title isn't a custom title and doesn't appear in `session_title`." [read: hooks page, "SessionStart input" and "UserPromptSubmit input"; types `:11648`, `:14668`]. A mod reads it through `on('classic.SessionStart')` or `on('classic.UserPromptSubmit')` [read: mods events page, "Handle the settings hook events"].
- **The status line command gets the generated title too.** `session_name`: "Uses the custom name … when one exists, otherwise the AI-generated session title" [read: https://code.claude.com/docs/en/statusline, "Available data"]. The status line is a settings command, not part of the mod API. Whether it runs in the desktop app is undocumented (section 1.7).
- **Generated titles in the CLI.** They are "a short summary of your first prompt, written by a background request to the small/fast model". Accepting a plan replaces the title. `/clear` keeps a custom name "but not an AI-generated session title" [read: sessions page, "Name your sessions" and "/clear"].
- **Desktop titles.** "To rename a session, click the session title in the toolbar" [read: https://code.claude.com/docs/en/desktop, "Work in parallel with sessions"]. How the desktop's `titleSource` `auto`/`user` relates to the engine's custom or generated title is undocumented. Locally: `titleSource` is `auto` 710, `user` 21, absent 262; `title` is present in 992 of 993 records [local].
- **Remote Control titles.** The remote session title is picked in this order: `--name` / `/remote-control <name>`, then `/rename`, then "the last meaningful message", then an auto-generated host name. A rename on claude.ai flows back to the CLI [read: https://code.claude.com/docs/en/remote-control, "Connect from another device"].
- **The desktop session id.** Nothing official lets a mod learn the desktop's `local_…` id, or tell which desktop session it belongs to [read: absent from the types, the mods reference and the desktop page].
- **What a mod can learn.** That it is drawn by a desktop client: `$.session.surfaces()` includes `desktop` once the app attaches, and `session.attach` fires with `surface` (types `:2806`, `:10703`; "the desktop app connected"). "A mod that draws can check which app it's running in" [read: mods overview, "Where mods run"]. Locally, desktop transcripts carry `"entrypoint": "claude-desktop"` (5 of 7 figures ids checked) [local], but no doc names that field as a contract.

### 1.3 Context figures

- **`$.session.usage()` returns the status line's figures.** It returns `{ startedAt, context, rateLimits, cost }`. "The plain call costs nothing; `"full"` counts each category with the token-count API as /context does, `"summary"` estimates locally" [read: types `:2826`–`:2845`; mods reference `$.session` row].
- **`context.tokens`.** "Input tokens the last response was answered over: uncached, cache-written and cache-read together (the status line's `total_input_tokens`)". `window` is the model's context window (`context_window_size`). `percent` is `tokens` over `window` as a whole percentage (`used_percentage`). Both `tokens` and `percent` are "absent until the first response of the live window: a fresh session, or one just compacted, until its next response" [read: types `SessionContextUsage` `:10943`–`:10972`].
- **The statusline page agrees.** "`used_percentage` … calculated from input tokens only: `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`. It does not include `output_tokens`." The window is "200000 by default, or 1000000 for models with extended context" [read: statusline page, "Context window fields"].
- **`breakdown.autoCompactThreshold`.** "The token count at which auto-compaction runs; absent when it is off." The breakdown "measures against the compaction window (`rawMaxTokens`), which may be smaller than `window`, and estimates every category, so its `totalTokens` need not equal `tokens`" [read: types `:10866`–`:10930`, `:10966`–`:10972`].
- **`session.measure` (`e.context`, `e.rateLimits`, `e.cost`, `e.changed`).** It fires "after each main-thread turn, and when a rate-limit window moves a whole point… One at a time, a burst folding into one more". `e.context` never carries `breakdown`. `changed` lists the units that moved (`context`, `rateLimits`, `cost`); the first measurement names every unit [read: types `:4405`, `SessionMeasureInput` `:11095`–`:11130`; mods reference: "After each turn, and when a plan limit's percent used changes"].
- **The desktop's own figure.** "Click the usage ring next to the model picker to see your current context window usage… Context usage is per session" [read: desktop page, "Check usage"].
- **`$.fs.write` is not atomic.** "`write` isn't atomic: it replaces the file's content in place, so another process can read a partly written file." [read: mods reference, `$.fs` row]. The overlay must tolerate half-written figures files [inference].

- **Sites.** `ui.render` components are `AskUserQuestion`, `UserMessage`, `AssistantMessage`, `ToolUse`, `ToolResult`, `ToolGroup`, `ToolProgress`, `CommandOutput`, `Spinner`, `TurnDuration`, `InfoNotice`, `SessionMode`, `PromptHint`, `AbovePrompt`, `Pane` [read: types `RenderComponent` `:9360`].
- **`SessionMode` draws on the desktop too.** It is "The dim mode labels at the right of the prompt footer (`focus`, `memory paused`)… One instance… Raised on the terminal and desktop surfaces only" [read: types `:10190`–`:10205`]. The mods reference "Render sites" table lists `SessionMode` as rendered on "Terminal, Desktop" [read: mods reference line 241].
- **`AbovePrompt`** is "The band directly above the prompt input… Raised on the terminal and desktop surfaces only" [read: types `:10255`]. The reference lists it on Terminal and Desktop [read].
- **Terminal-only sites** are `ToolProgress`, `TurnDuration` and `InfoNotice`. The desktop has no `Raster`; `Svg` is desktop-only [read: mods reference "Render sites" and "Elements"; mods interface page].
- **Drawing per surface.** "Hooks run" and "What the mod draws appears" are both "Yes" for the Desktop Code tab, "except in a WSL session". Remote Control from claude.ai or mobile: hooks run "in the session on your machine", drawings show "In the terminal on your machine" [read: mods overview, "Where mods run"].
- **Desktop sessions are SDK-hosted.** The hooks page calls the SDK's `canUseTool` "how Claude Desktop and the VS Code extension host Claude Code" [read: hooks page, Notification section]. `SessionStartInput.surface` is "`terminal` under the REPL; null for a `-p` run or the SDK, which draw nowhere yet" [read: types `:11671`–`:11690`]. So in a desktop session `session.start` most likely sees `surface: null`, and the desktop arrives later through `session.attach` [inference].
- **`$.ui.status`** pins one line under the prompt and draws "10000 [characters] remotely" [read: types `:2467`; skill `reference.md` line 130]. That implies it draws on remote surfaces such as the desktop [inference].

### 1.5 Plugin loading and pickup by running sessions

- **Three stages.** Declared in settings (`enabledPlugins`, `extraKnownMarketplaces`), then fetched to disk (`installed_plugins.json`, `known_marketplaces.json`, `cache/`), then loaded in the running session. "Changes to settings or to disk don't reach this layer until you run `/reload-plugins` or start a new session." [read: https://code.claude.com/docs/en/plugins/loading, "Check which stage a plugin reached"].
- **Installing while a session is open.** "If you install or update a mod from your shell while a session is open, run `/reload-plugins` in that session to load it. Otherwise it loads the next time you start Claude Code." [read: mods overview, "Install or update a mod"]. The install docs say the same [read: plugins/install].
- **`/reload-plugins` works in the desktop app.** Since v2.1.260 it "also runs in sessions without an interactive terminal, such as the desktop app". There, "the command runs only when you type it into the session yourself… When it arrives another way, such as through Remote Control… the command replies `/reload-plugins isn't available over a remote connection in this session.`" [read: https://code.claude.com/docs/en/plugins/cli-reference, "/reload-plugins", "Sessions without an interactive terminal"].
- **Desktop can reload open sessions by itself.** Changelog 2.1.274 (September 17, 2026): "Fixed `installed_plugins.json` being rewritten on nearly every start-up… which made Claude Desktop reload every open session's plugins" [read: changelog]. The app's code has an `installedPluginsWatcher` and `broadcastReloadPlugins`, which sends the SDK `reload_plugins` request. It is gated by a feature flag and by managed MCP policy, and throttled [code: `app.asar`]. No docs page states this behavior.
- **`/plugin` in the desktop app.** "a local session the desktop app starts for its Code tab answers that the command is not available there. A mod installed from a terminal at the user scope loads in that local session too, and its `ui.render` hooks draw for the `desktop` surface." [read: skill `reference.md` line 105]. Desktop installs plugins through **+ > Plugins** [read: desktop page "Install plugins"; plugins/install "Desktop app" tab]. The VS Code tab says changes "apply to open sessions without a restart"; the Desktop tab says nothing about open sessions [read: plugins/install].
- **A local directory marketplace loads in place.** "Relative-path plugins in a marketplace you added from a local path: the plugin loads in place from its path inside the marketplace folder. Your edits to the source directory take effect at the next session start or `/reload-plugins`" [read: plugins/loading, "In-place and copied plugins"; skill `reference.md` line 76]. So the copy at `~\.claude\plugins\cache\claude-code-plus\context-bar\0.1.0` is a record, and sessions run `C:\Projects\ClaudeCodePlus\mods\context-bar` itself [inference from read]. Locally: `installed_plugins.json` has `context-bar@claude-code-plus` with scope `user`, `installPath` under that cache folder, version 0.1.0, `installedAt` 2026-10-15T12:03:14.022Z and `gitCommitSha` bcf9b05. `known_marketplaces.json` has `installLocation` `C:\Projects\ClaudeCodePlus` [local].
- **`CLAUDE_CODE_PLUGIN_DIRS`** gives "Plugin directories to load for the session, each loaded the way a `--plugin-dir` flag loads it… `;` on Windows… absolute path or start it with `~`… Requires Claude Code v2.1.280 or later" [read: env-vars page]. It is read from the "Environment, or `env` in `~/.claude/settings.json`" and is "for apps you can't pass a flag to" [read: mods reference, "Settings and environment variables"]. Project and local settings cannot set it [read: plugins/create].
- **Plugins from `CLAUDE_CODE_PLUGIN_DIRS` are session-only (`@inline`).** They replace a same-named installed marketplace plugin silently [read: plugins/loading, "Name conflicts"].
- **Env changes in settings.json.** "A running session applies new and changed values to its environment when you save the file… Removing a variable from the file doesn't unset it in a running session" [read: env-vars, "Set variables in settings files"]. Plugins still load only at start or `/reload-plugins` [read]. So adding `CLAUDE_CODE_PLUGIN_DIRS` mid-session would at most take effect at that session's next `/reload-plugins` [inference; undocumented].
- **Locally the key is gone.** `settings.json` today has `env` keys `BASH_ENV` and `CLAUDE_PLUGIN_DATA` only, and no `CLAUDE_CODE_PLUGIN_DIRS`. The file was last written 2026-10-15T12:03:13Z, one second before the marketplace install [local].
- **Hot reload.** A `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` folder is watched in interactive sessions. "a long-lived headless session (SDK, desktop) watches too when `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` is set" [read: skill `reference.md` line 72; env-vars `CLAUDE_CODE_PLUGIN_DIR_WATCH`]. A reload "is a fresh load of the module: `register` runs again and `session.start` fires again. Values in `$.state`… and `$.store`… stay; the module's own variables start over" [read: skill `SKILL.md`].
- **`$.store`.** "This plugin's own key-value store, kept between sessions and hot reloads… A JSON file of the plugin's own under the user's Claude Code configuration directory" [read: types `:3345`]. "A key-value store that every session on the machine shares" [read: mods reference `$.store` row]. It is per plugin and per config dir, shared across sessions, and `get`+`set` is not atomic [read: mods interface, "Save from more than one session"].
- **Checking whether a mod loaded.** `/plugin` shows `N mods active · <names>` in a terminal session [read: mods overview]. In the desktop `/plugin` is unavailable, so the check is the mod's own command (`/ctxbar`) or the debug log [inference from read].

### 1.6 Hooks in desktop sessions

- **Settings hooks run in the desktop app.** "Claude Code fires the same hook events wherever it runs: sessions in the terminal, IDE extensions, the Desktop app, and cloud sessions" [read: hooks page, intro]. Settings-file hooks "apply to both" the desktop and the CLI [read: desktop page, "Shared configuration"].
- **Mod hooks run in the desktop Code tab, except in WSL sessions.** "plugins aren't available in WSL sessions" [read: mods overview, "Where mods run"].
- **SSH sessions run a copy.** Desktop copies plugins to the remote machine at `~/.claude/remote/plugins/` [read: desktop page, files table]. A mod there runs on the remote machine and writes to that machine's config dir [inference].
- **Plugin-supplied title fields need an early install.** "If your plugin's SessionStart hook supplies `initialUserMessage` or `sessionTitle`, install the plugin before the session starts." [read: hooks page, "SessionStart decision control"].
- **Notifications have no channel in the desktop.** `$.ui.notify` answers `no-surface` in "a `-p` run, the SDK, the desktop" [read: types `:14106`].

### 1.7 The status line in the desktop app

- **The docs describe the status line for the terminal only.** It "renders in its own row above the built-in footer badges". It runs at session start, on each new assistant message, after `/compact`, on permission-mode change and on similar events, "debounces updates at 300ms" and can run on `refreshInterval` [read: statusline page, "When the status line updates"]. The settings reference files `statusLine` under "Interface and terminal" [read: settings-reference].
- **Undecided for the desktop.** Neither the desktop page nor the statusline page says whether the `statusLine` command runs, or is drawn, in the desktop app. The desktop documents its own usage ring instead [read: desktop page]. This is a documentation gap, not a finding.

### 1.9 Remote Control and other session kinds

- **Remote Control is a window onto a local session.** "Remote Control sessions run directly on your machine… The web and mobile interfaces are a window into that local session" [read: remote-control page, intro]. In the desktop app you turn it on with `/remote-control` or `/rc`, or through **Settings > Claude Code > Connect new sessions to Remote Control** [read: remote-control page "Desktop app" tab; desktop page "Control which sessions appear on your other devices"].
- **Resuming keeps the claude.ai session.** "When you resume a conversation in Claude Desktop or an IDE extension that had Remote Control on, Claude Code reattaches it to the existing claude.ai session instead of adding a new one" [read: remote-control page].
- **Remote Control id in subprocesses.** `CLAUDE_CODE_BRIDGE_SESSION_ID` is set in Bash and hook subprocesses while Remote Control is connected, in `session_…` form [read: env-vars; hooks page]. The `$.session.send` address accepts "a Remote Control or cloud id (`session_...`)" [read: types `:11513`].
- **Mods under Remote Control.** Hooks run in the session on your machine [read: mods overview table].
- **Session kinds in the Code tab.** Local, cloud, SSH, WSL (Windows), Dispatch-spawned (sidebar badge **Dispatch**) and scheduled-task runs [read: desktop page, "Start a session", "Sessions from Dispatch", desktop-scheduled-tasks]. ### 1.10 Chromium and Electron UI Automation mapping on Windows

The Chromium source was read at `HEAD` on 2026-10-15. The Chromium version inside Claude 2.37337.1 was not checked, so treat these as current Chromium behavior.

- **UIA `Name`** is the node's computed accessible name: aria-labelledby, aria-label, content, title and so on, per the accname rules. List items get a computed name [code: `ui/accessibility/platform/ax_platform_node_win.cc:5544`].
- **UIA `AutomationId` is the DOM `id`.** `UIA_AutomationIdPropertyId` returns `GetAuthorUniqueId()`, except the document root, which answers the constant `"RootWebArea"` [code: `ax_platform_node_win.cc:5331`–`:5340`]. `GetAuthorUniqueId()` returns the `kHtmlId` string attribute [code: `ax_platform_node_delegate.cc:632`–`:634`]. Blink fills `kHtmlId` from `element->GetIdAttribute()` for every non-ignored node that is not static text, outside screen-reader mode too ("Needed on Android for testing frameworks") [code: `third_party/blink/renderer/modules/accessibility/ax_object.cc:1321`–`:1324`, `:1608`–`:1617`].
- **`data-*` attributes (such as `data-testid`) are not exposed as UIA properties.** Other HTML attributes go only into a snapshot list and a short JAWS allow-list [code: `ax_object.cc:1620`–`:1660`].
- **UIA `ClassName` is the HTML `class` attribute**, serialized only in extended-properties (screen-reader) mode [code: `ax_object.cc:1328`–`:1339`, `:1589`–`:1606`; `ax_platform_node_win.cc:5342`].
- **The `Document` element's Name is the page title.** The root web area's name is the `aria-label` on `<html>` if there is one, else `document.title` [code: `ax_node_object.cc:7778`–`:7805`].
- **Title changes raise a Name-changed event.** A title change posts `kDocumentTitleChanged` [code: `ax_object_cache_impl.cc:2624`–`:2630`]. On Windows a name change fires a UIA property-changed event for `UIA_NamePropertyId` [code: `browser_accessibility_manager_win.cc:575`–`:580`]. So a poller sees the new title on its next read, and a client can also subscribe to `NamePropertyChanged` on the Document [inference from code].
- **The native window title.** Electron's `page-title-updated` is "Emitted when the document changed its title"; preventing it keeps the native window title unchanged, and "The title of the web page can be different from the title of the native window" [read: https://www.electronjs.org/docs/latest/api/browser-window]. Whether Claude's window title follows the page title is unverified.
- **Microsoft on `AutomationId`.** It "uniquely identifies a UI Automation element from its siblings" and "does not guarantee a unique identity throughout the tree; it typically needs container and scope information" [read: https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/use-the-automationid-property, updated 2026-03-30].
- **The app is localized.** Its `resources` folder ships per-locale JSON files (`am.json`, `bn.json`, …) [local]. Accessible names such as "Environment: …" and "Model: …" are therefore likely to change with the UI language [inference].

### 2.2 Issue #2 (Context line missing in a session: no figures file, no store record)

- **Hypothesis A (the mod is not loaded in that session): plausible and documented as a mechanism.** A running session keeps the plugin set from its start or its last `/reload-plugins` [read: plugins/loading]. `CLAUDE_CODE_PLUGIN_DIRS` loads "for the session" like `--plugin-dir` [read: env-vars]. A session whose engine started before the 09:21Z (12:21 local) settings edit would not have the mod [inference]. The 12:03Z marketplace install can reach open desktop sessions through Desktop's `installed_plugins.json` watcher, which is flag-gated and throttled [read: changelog 2.1.274; code]. That weakens A for any time after 12:03Z, unless the flag is off.
  - **Documented remedy:** type `/reload-plugins` in that session's own prompt box. It is refused over Remote Control [read: plugins/cli-reference]. Or start a new session.
  - **Documented test:** the mod's `/ctxbar`. "Unknown command" means A. `/plugin` does not exist in the desktop.
- **Hypothesis B (the session has no desktop store record): undecided by the docs.**
  - The store is undocumented, so no official source defines which session kinds get a `local_` record [read: absence].
  - The "Remote Control" variant is contradicted by local data: Remote Control sessions do get records with `bridgeSessionIds` [local].
  - Kinds that might live elsewhere: cloud sessions, CLI sessions, and sessions on another machine. On SSH, the mod writes its figures on the remote machine [inference].
  - B alone does not explain "no figures file". The mod writes its file whatever the store holds. "No file and no record" therefore points to A, or to a session whose mod writes somewhere else: SSH or another config dir [inference].
- **Hypothesis C (layout): undecided.** No docs cover the footer's layout. The desktop does raise `SessionMode`, the footer mode-label slot, for mods [read: types `:10190`–`:10205`], so `/ctxbar footer` is a documented in-app fallback that layout cannot defeat.
- **Hypothesis D (not in the issue): the 4th problem.** If that session ever ran `/clear`, `/resume` or `/branch` after its mod loaded, the mod keeps its old id (section 2.4). The figures land in a file the store no longer names [inference from read].
- **Reproduction caveat [local].** Issue #2's facts do not match this machine (`MSI`, 14:00Z):
  - The store holds 993 `local_*.json` records here, not 2108.
  - No record has `cliSessionId` or file name `68ec5dbf…`, and no title contains "gemini tab reload", "reload" or "google check trigger" (counts only).
  - `~\.claude\context-bar\` holds none of `128e1e6d`/`0c7a89d9`.
  - So the issue was likely observed on another machine, or the folders changed since. Re-check B there [inference].
- **The sanctioned approach.**
  - For loading: install once at user scope from a terminal (done 12:03Z), then type `/reload-plugins` in older sessions [read].
  - For mapping: let the mod draw in the app (`SessionMode` or `AbovePrompt`), so the line follows the session that draws it with no mapping [read: render sites].
  - If the overlay stays, the mod can publish the custom title from `classic.SessionStart`/`classic.UserPromptSubmit` `session_title` [read: hooks page]. The documented API does not expose the auto-generated title, which most desktop sessions show (`titleSource: auto` in 710 of 993 records [local]). So the issue's proposal to write the title into the figures file only works for renamed sessions [inference from read].

### 2.3 Issue #3 (Context line shows the previous session's figures while a new session is starting)

- **What the docs say.** A fresh session has no context reading: `tokens` and `percent` are "absent until the first response of the live window: a fresh session, or one just compacted" [read: types `:10943`–`:10950`]. The statusline doc says the same of `current_usage` and `used_percentage` [read]. So "—" is the documented truth for a starting session, and another session's figures are never right [inference from read]. This **confirms the issue's proposed rule**: never fall back to a different session.
- **Can the page title be read during "Starting session"?** On the platform side, yes: the `Document` element exists and its `Name` tracks `document.title` with a Name-changed event [code: section 1.10]. Which string the app sets is undocumented.
  - It could be the previous session's title (a stale page), a blank title (new session with no title yet), or a generic one.
  - The app's code emits `initialization_status` events with the message "Starting session..." [code: `app.asar`].
  - Check 1 of the issue (dump the Document name during start) stays necessary [inference].
- **Hypothesis "its store record has no `cliSessionId` yet".** Undecided. The 22 records without one on `MSI` are all old (≤ 2026-05-30), so they are not evidence of a transient start state [local]. Watching a new record during start (check 2 of the issue) stays necessary.
- **Hypothesis "its title is not written yet".** Undecided. Docs: the CLI's generated title comes from "a background request to the small/fast model" after the first prompt [read: sessions page]. If the desktop titles the same way, a delay of seconds is expected [inference].
- **The sanctioned approach.** Draw "—" or hide when the record has no `cliSessionId` or no figures file; never fall back to another session. With no readable title, hide as well [inference from read]. The in-app `SessionMode` footer avoids the problem entirely, because each session's mod draws only its own reading [read: render sites; inference].
- **Undocumented contracts.** The page title format `"<title> - Claude Code"` (`FooterLocator.cs:32`, `:40`–`:47`); the store's `title`, `cliSessionId`, `lastFocusedAt` and `isArchived` (`FocusedSessionFinder.cs:79`, `:97`); the `claude` process name.

### 2.4 The possible 4th problem: the engine session id changes inside one desktop session

- **Confirmed by the docs.** `/clear`, `/resume` and `/branch` move the process to another session id without a new `session.start`, and reset `$.state` [read: mods reference Session table; troubleshoot; types `SessionEndInput`]. `CLAUDE_CODE_SESSION_ID` "is updated on `/clear`" [read: env-vars]. On the desktop side, "Clearing session" and rewind record the old id in `priorCliSessionIds` [code]. 4 records on `MSI` show it happened [local].
- **The effect in this mod** [inference from read code plus docs]:
  - `session` is cached at `register.tsx:147` and learned only in `session.start` (`register.tsx:304`).
  - After `/clear`, `reading` resets to `null`, so `publish` skips until the next measurement. Then it writes the new conversation's figures to `<old id>.json`.
  - The desktop record's `cliSessionId` names the new id, so the overlay finds no file and shows no line. If an older file under the new id existed, it would show stale figures.
  - After compaction the id stays and `tokens` is absent until the next response, so the file shows `tokens: null` for a moment [read].
- **The sanctioned fix.** Add a `classic.SessionStart` hook with `{ source: ['clear', 'resume', 'fork'] }` that re-learns `id`, `cwd` and `model` and re-reads the store values [read: mods interface "Load a saved value again after `/clear`"]. Or call `$.session.id()` in `publish` every time; it is cheap, though no doc gives its cost. Optionally add a `session.end` hook (reason `clear`/`resume`) that marks the old file ended, for example with `isHidden: true`. Never delete. It has a 1.5 s budget [read: hooks page "SessionEnd input"; types `SessionEndInput`].
- **Overlay side.** Keying on the current `cliSessionId` is correct once the mod writes under the current id. Falling back to `priorCliSessionIds` would show the previous conversation's figures, the same error as issue #3 [inference].

## 3. Documentation gaps and risks

1. **The desktop session store is undocumented**, both its location and its schema. Every field the overlay reads (`title`, `cliSessionId`, `lastFocusedAt`, `isArchived`) can change in any app update, and the code already knows fields we do not handle (`unarchivedCliSessionId`, `preClearCliSessionId`) [read: absence; code].
2. **No documented way for a mod to learn its desktop session id or its displayed (auto) title.** Only the custom title (`session_title`) is reachable [read].
3. **Whether Desktop pushes plugin installs to open sessions** is stated only indirectly, in a changelog fix note. The code shows it behind a server-side flag [read: changelog 2.1.274; code]. Do not rely on it; tell users to type `/reload-plugins`.
4. **The status line in the desktop app is undocumented** (section 1.7).
5. **`claude://code/new?folder=` is undocumented.** Only SSH parameters and `q` are documented [read].
6. **Accessible names are neither a contract nor language-stable.** The app ships locale files [local]. Chromium's `AutomationId` is the DOM `id` [code], but whether Claude's controls have ids is unverified.
7. **`$.fs.write` is not atomic** [read]. The overlay must treat a JSON parse failure as "keep the last good value", not as "no figures".
8. **API churn.** "EARLY ACCESS: this surface may change between releases without notice" [read: types header]. The docs (v2.1.290 reference, changelog to 2.1.300) already describe features newer than this engine (2.1.295), such as `$.session.identity()` in 2.1.299 [read: changelog]. Check each API against the types file this engine writes.
9. **`$.store` is shared by every session on the machine** [read]. `/ctxbar off` and placement in one session affect the next `session.start` of every session. That is intended per the README, but it is a race if two sessions write at once [read: mods interface "Save from more than one session"].
10. **Packaged-app file views.** This research ran inside the packaged app's process tree. The store counts it saw (993) differ from issue #2 (2108). The package's `LocalCache` holds `Local` only, no `Roaming` [local], so `%APPDATA%` virtualization is unlikely to explain the gap. Confirm counts on the machine where an issue was seen [inference].
11. **The Chromium source was read at `HEAD`, not at the version inside Claude 2.37337.1** (section 1.10).
