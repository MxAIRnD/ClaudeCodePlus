## 0. Summary and recommendations

**The one finding that changes the plan.** The session the app shows can be identified by its **id**, not by its title. The page's UI Automation `Document` element (the one named `"<title> - Claude Code"`) has a `ValuePattern` value of `https://claude.ai/epitaxy/local_<uuid>`, and `local_<uuid>` is the desktop store record's id [prec §2.0, confirmed twice on MSI: local]. The engine of that session runs with `CLAUDE_CODE_HOST_SESSION_ID=local_<uuid>` and `CLAUDE_CODE_SESSION_ID=<engine id>` in its environment [local: this session's own environment], and keeps a live registry `~\.claude\sessions\<pid>.json` with `hostSessionId`, `sessionId`, `name`, `status`, `startedAt`, `procStart` [local]. If the mod publishes its figures under the host id and the overlay reads the host id from the Document's URL, the title, the store record and the engine id drop out of the mapping. That removes the race in #3, the "no record" case of #2 and the id-change staleness of the 4th problem at once. No existing tool was found that does this or that makes the overlay or the mod unnecessary [prec §0, §1].

## 2. Issue #1 (Button hidden on the new-session screen when no folder is selected)

**What is known.** Filed on app 2.26454.2 (older layout): with no folder the row is only `Local · No folder`, and the anchors `Add another folder` and `worktree` appear only after a folder is picked. Since then `f833f53` (2026-10-14, app 2.37337.1) added a third anchor: the `Environment: …` chip joined with the buttons that follow it on its row (`src/Feature.ChipButton/ChipRowLocator.cs:68-82`) [code]. The docs name the new-session controls but say nothing about their accessible names or tree, and no mod can draw there (render sites belong to a running session) [docs §2.1].

**Whether it still reproduces.** Unverified. On 2.37337.1 the environment chip belongs to the composer's bottom row whether or not a folder is picked, so the anchor should exist with no folder [inference]; one capture settles it (section 8, check B).

**No sturdier anchor than names.** Chromium maps the UIA `AutomationId` to the DOM `id` only, `data-testid` is not exposed, and `ClassName` is the HTML class attribute [docs §1.10, prec §2.1]; here the ids are React `useId` values that change between mounts, and the classes are Tailwind strings [local]. Microsoft's own guidance: `AutomationId` identifies an element among its siblings and needs container scope [prec §2.1]. So accessible names with structural fallbacks, which `ChipRowLocator` already does, remain the norm; the missing piece is diagnosability [prec §2.1]. Risks to note: an app update can rename a chip (the model chip already reads `Model: Fable 5.1 Max`, which the prefix match survives) and the app ships 43 locale files, though the chip names are not in those files, so whether they are translated with the UI language is unknown [prec §2.1].

**Recommendation.**
1. Capture the no-folder screen on 2.37337.1 (check B). If `Environment: …` is present, record in #1 that `f833f53` covers current builds; keep the issue's `No folder` fallback (never the one in a session header) only if the older layout must stay supported.
2. Self-diagnostic in both locators, adapted from pywinauto's `print_control_identifiers()` [prec §2.1]: when a Claude window is in front and no anchor (or no footer slot) is found, log once per app version the names and bounds of the buttons on the lowest composer row, with the app version (readable from the shell document's URL `Claude_2.37337.1.0_x64__…` or the process image path). A renamed chip then becomes a one-line report instead of a silent disappearance.
3. Optional: a name table keyed by app version (and locale once known), so a rename is a data change.

## 3. Issue #2 (Context line missing in a session: no figures file, no store record)

**Hypothesis A, the mod was not loaded: likely, documented, with a cheap test and a fix without restart.** A running session keeps the plugin set it loaded at start or at its last `/reload-plugins`; settings and disk changes do not reach it [docs §1.5]. `/reload-plugins` works in desktop sessions since 2.1.260 when typed in the session's own prompt box, and is refused over Remote Control [docs §1.5]; two reporters run it in desktop sessions (anthropics/claude-code #96223 "Desktop sessions load the install-time cache copy of local-directory marketplace plugins instead of loading in place", #100926 "plugin userConfig rows missing until /reload-plugins in desktop-hosted and headless sessions") [prec §2.2]. The desktop can also reload open sessions' plugins by itself when `installed_plugins.json` changes (changelog 2.1.274; `installedPluginsWatcher` in `app.asar`, behind a feature flag) [docs §1.5]; on MSI a record created before the 12:03Z install publishes figures, which fits that or a restart [docs §1.8]. The in-session test is `/ctxbar` ("Unknown command" = not loaded); `/plugin` does not exist in the desktop [docs §2.2]. Outside the session, the registry gives the engine's `startedAt` to compare with the mod's `installedAt` (`2026-10-15T12:03:14Z`) [prec §2.2]. Complication to know: #101640 reports mods loading but never running in the desktop Code tab on macOS 2.31226.1, and #99130 a server-side rollout switch turning mods off; on this Windows build mods run (figures files exist for all six live engines) [prec §2.2].

**Hypothesis B, no store record: contradicted for Remote Control; moot with id-based mapping.** 798 of 993 records on MSI carry `bridgeSessionIds`, so sessions with Remote Control on do get records [docs §1.8]. Sessions started in a terminal, or Remote Control rows a terminal session registered, have no desktop record (#101326, #101862) [prec §2.2]; mods run on the host for those but draw nothing in the desktop view (#99217) [prec §2.2]. B alone cannot explain "no figures file": the mod writes its file whatever the store holds [docs §2.2]. With the Document URL as the key, a session whose URL is not `epitaxy/local_…` is known to be another kind and shows nothing on purpose; what the URL is for such rows is open (section 8, check C).

**Hypothesis C, layout: unlikely.** The screenshot's row was wide; `FindSlot` needs three chip heights [code]. No precedent found [prec §2.2].

**The issue's facts are from another machine.** MSI holds 992-993 records, not 2108; no record `68ec5dbf`; none of the figures ids named in the issue [docs §2.2, local]. Re-check on the LG laptop in the affected session: `/ctxbar`, then `~\.claude\sessions\` for its engine and `startedAt`.

**The title-in-figures idea does not work.** A mod reaches only the custom title (`session_title` in `classic.SessionStart` / `classic.UserPromptSubmit`); the auto-generated title that most records show (`titleSource: auto` 710 of 993) is not exposed to mods [docs §1.2]. The host id replaces it.

**The 4th problem can look like #2.** After `/clear`, `/resume` or `/branch` the mod writes under the old engine id while the record names the new one: no file where the overlay looks [docs §2.2, §2.4]. Section 5.

**Recommendation.**
1. README "Line missing in a session": type `/ctxbar`; "Unknown command" means the session started before the mod was installed or enabled, so type `/reload-plugins` in it (not over Remote Control) or start a new session.
2. With id-based mapping, the overlay can distinguish and log: shown `local_` id but no figures file (mod not running there: not loaded, SSH session writing on the remote machine, or another config dir); file present with `tokens: null` (no reading yet, draw "—"); no `local_` URL (not a local session, hide). Optionally look the id up in `~\.claude\sessions\*.json` by `hostSessionId` to add `startedAt` to the log line, with the pid-reuse guard (`procStart`) from claude-watch [prec §2.2, §3].
3. Close B as "not reproduced on MSI; re-check on the LG laptop" once that check is done.

## 4. Issue #3 (Context line shows the previous session's figures while a new session is starting)

**Confirmed.** `FocusedSessionFinder.Pick` (`src/Feature.ContextBar/FocusedSessionFinder.cs:71-98`) answers the newest-focused record of all when the shown title matches none; records without `cliSessionId` are skipped first [code]. The docs say a fresh session has no context figures until its first response (`tokens` and `percent` absent) [docs §1.3], so for a starting session the only right outputs are "—" or nothing [docs §2.3]. Every tool read hides, shows a placeholder (`?`, `0% · 0 tokens`), or keeps the same session's last value marked stale; none borrows another entity's value; monitoring systems mark staleness instead of carrying values over [prec §2.3].

**Which half of the race.** Unsettled, and less important with the id:
- *No `cliSessionId` yet.* The 22 records without one on MSI are old sessions whose transcripts became unavailable (`transcriptUnavailable: true`, #92825), not sessions caught while starting [docs §1.8, prec §2.3]. So that line of the issue's evidence does not show the start state; whether a new record lacks the id for seconds is unverified (check A).
- *No title yet, or a stale page title.* The generated title comes from a background request after the first prompt [docs §1.2]; some builds never title (262 records here have no `titleSource`) [prec §2.3]. The page title is readable at any moment (Chromium keeps the Document's Name equal to `document.title` and raises a Name-changed event) [docs §1.10]; what the app puts there during "Starting session" is unknown (check A).
- *The URL.* The `local_` record id exists as soon as the route does, before any title or engine id [prec §2.3, inference]; whether the session document already carries `epitaxy/local_<uuid>` during "Starting session" is check A's main question.

**The fix.**
1. *Structural (recommended).* `FooterProbe` adds `ValuePattern.ValueProperty` to its cache request (`FooterProbe.cs:66-74`; Documents are already fetched, `:22-26`); `FooterLocator.ShownSessionId(elements)` returns the `local_<uuid>` of the first Document whose value matches `^https://claude\.ai/epitaxy/(local_[0-9a-f-]{36})$`; `ContextBarForm.ReadFigures` opens `<figuresRoot>\<local id>.json`. No title, no store, no fallback; no `local_` URL means hidden. `FocusedSessionFinder` and its tests retire (or stay as a fallback for a build without the URL, owner's call). Tests: the id parse (session document, shell document, no document, a non-local route) and the form's three states (no id, id without file, file with `tokens: null`).
2. *Interim, as the issue proposes, if the title path stays for a while.* In `Pick`: answer only a namesake when a title is known; a namesake without `cliSessionId`, or no namesake, answers null; keep "newest of all" only for the no-title case or drop it (the titled Document exists whenever a session is shown [local], so "no title" means "no session shown"). The issue's two tests plus "title matches only a record without `cliSessionId` → null". README: "nothing when the title matches none".

**What the user sees after the fix.** Hidden during the start; then "—  — / 1M" once the mod has published its first, empty reading; then the figures. Honest, and the same sequence `best-claude-hud` uses for a new session [prec §2.3].

## 5. The 4th problem: the engine session id changes inside one desktop session (filed as #4, https://github.com/MxAIRnD/ClaudeCodePlus/issues/4)

**Documented.** `session.start` fires "Once for each loaded mod, before the first prompt, and again after a reload of that mod. Not after `/clear`, `/resume`, or `/branch`" (mods reference). After those the process goes on under a new session id, `$.state` resets, and `classic.SessionStart` fires with `source` `clear`, `resume` or `fork` [docs §1.1]. `CLAUDE_CODE_SESSION_ID` "is updated on `/clear`" [docs §1.1]. The desktop records the old id in `priorCliSessionIds` on "Clearing session" and rewind; 4 of 993 records on MSI show it; store readers name the lineage fields `preClearCliSessionId`, `priorCliSessionIds`, `unarchivedCliSessionId` [docs §1.1, prec §2.4]. Engine ids can even collide across concurrent desktop engines while host ids differ (#102198) [prec §2.4].

**Effect in `register.tsx`.** `session` (id, cwd, model, file) is learned once in `session.start` (`mods/context-bar/hooks/register.tsx:147`, `:157-168`, `:290-305`). After `/clear` the `reading` atom resets, so `publish` skips until the next measurement, then writes the new conversation's figures to `<old id>.json`; the record names the new id, so the overlay finds no file and hides, or shows a stale file if one existed under the new id [docs §2.4]. The `isHidden` and `placement` atoms reset to their defaults as well and are re-read from `$.store` only in `session.start`, so `/ctxbar off` silently turns back on after `/clear` [prec §2.4]. Whether `$.session.id()` returns the new id after `/clear` is unverified [prec §2.4].

**Fix.**
- `on('classic.SessionStart', { source: ['clear', 'resume', 'fork'] }, async ($, e, next) => { … })` that re-runs `learnSession`, reloads `isHidden` and `placement` from `$.store`, refreshes and publishes: the pattern the mods "Draw in the interface" page documents for reloading a value after `/clear` [docs §1.1, prec §2.4]. A matcher is required for a second registration of an event [prec §2.4]. `e.session_id` is available there too.
- In `publish`, compare `await $.session.id()` with the cached id and re-learn on a difference (cheap; cost undocumented) [docs §2.4].
- Key the figures file by the host id (`CLAUDE_CODE_HOST_SESSION_ID`, read through `$.env.get`, as the mod reads `CLAUDE_CONFIG_DIR` today; the types document `$.env.get` as "the environment of this process", with the name as a string literal that `claude plugin validate` lists, and no name filter [local: `types/claude-code.d.ts:3588-3610`]), falling back to the engine id when the variable is absent (a terminal session); keep `sessionId` (engine id) and `hostSessionId` inside the file. The host id stays fixed across `/clear` and differs even when engine ids collide [prec §2.4; stability across `/clear` is check D]. The overlay then never sees the change.
- Optional: `on('session.end', …)` with reason `clear`/`resume` marks the old engine-keyed file `isHidden: true` (never delete; 1.5 s budget) [docs §2.4]. Unneeded once the file is host-keyed.
- Never fall back to `priorCliSessionIds` in the overlay: that is #3 again [docs §2.4].
- Test in `bar.test.ts`: after a `classic.SessionStart` with `source: 'clear'` and `session.id` answering a new id, the next write carries the new engine id (same host-keyed file); and `isHidden` stays true when the store says so.

**Also worth noting.** Compaction keeps the id but leaves `tokens` absent until the next response, so the file shows `tokens: null` briefly and the line "—" [docs §1.1]. Intended.

## 6. Precedents and reusable solutions

**Nothing replaces the overlay or the mod** [prec §0, §1]. The large status-line tools (claude-hud 28.5k stars, ccusage 19k, ccstatusline 13k, claude-powerline 1.2k, best-claude-hud, CCometixLine, cc-statusline, howmuchleft) draw only in a terminal: the `statusLine` command renders nothing in the desktop Code tab (anthropics/claude-code #90708 "Desktop app: bring back the context-usage indicator", #91712). The desktop app itself stopped showing context in its usage ring on 2026-10-13/14 and moved it to the Session Rail panel, with open bugs (#102094 "context-window usage no longer shown anywhere", #102279, #102288, #102254, #102230 "Session Rail context progress bar does not update"). At least six context mods appeared between 2026-10-02 and 2026-10-15 (context-band, fredrikbonde/claude-context-bar, ContextLab, justerification, lrdub, k-wolfe99) plus Anthropic's sample `token-weather`; all draw a band above the prompt, none in the footer row, and the band is hidden while the desktop's next-step box is shown (#102249). Transcript-parsing tools (edenaion's VS Code bar, hatohato-lab's meter) must guess the window size from the model id; OpenTelemetry has no context-fill metric. The mod's figures source, `$.session.usage()` without a breakdown, is the same as the official status line and free (token-weather README) [prec §1].

**Reusable, in order of value:**
1. **Identify the session by id.** The `local_` id in the Document URL (section 0) and the same id in the engine's environment. Precedents key on the `local_` id for deep links and dashboards (claude-code-dashboard; `claude://code/continue?session=<local id>`), and a commenter running 200+ threads states the rule: "Titles are not ids" (#101545) [prec §2.0, §3].
2. **The live registry `~\.claude\sessions\<pid>.json`** joins `hostSessionId`, `sessionId` and `name`; claude-watch (macOS), claude-streamdeck (Windows) and hatohato-lab's meter read it, with a pid-reuse guard on the process start time (`procStart`) [prec §2.0, §3]. It is undocumented; the documented interface over the same data is `claude agents --json` ("the supported way to read session state from outside Claude Code, for example from a status bar"), which needs the `claude` CLI, not on PATH here (only the desktop's bundled engine) [prec §1]. For the overlay the registry is optional (diagnostics only), since the URL already gives the id.
3. **Never show one entity's figures under another**: hide, placeholder, or the same session's last value marked stale (claude-powerline, ccstatusline, best-claude-hud, ai-code-usage-tray "the last figures stay, marked with their age", Claude-Code-Usage-Monitor; Prometheus staleness) [prec §2.3, §3].
4. **Follow the id through `/clear`, `/resume`, `/branch`** with `classic.SessionStart` and `source` (the documented pattern); ai-code-usage-tray folds `priorCliSessionIds` into the current conversation; magpie lists the lineage fields [prec §2.4].
5. **Treat the desktop store as undocumented and migrating**: agent-git refuses to write `local_*.json` ("The format is unstable, and it is migrating"); hatohato-lab's reader blanks values on a format change instead of breaking [prec §3]. With the URL key the overlay stops reading the store at all.
6. **Plugins load at session start; `/reload-plugins` loads them into a running desktop session** (docs; #96223, #100926, #102240 "Seeded plugins need a manual /reload-plugins in every fresh session") [prec §2.2].
7. **Diagnosable anchors**: dump the candidate names when a lookup fails (pywinauto); record the app version; expect a thin tree on the first probe after an app start, since Chromium enables fuller accessibility modes only when a client asks for properties [prec §2.1, §3].
8. **Refresh triggers worth copying** from fredrikbonde's bar: after tool calls as well as turns and compaction [prec §1]; and #94424 asks Anthropic for an event when usage changes, which `session.measure` partly is [prec §1].

## 7. Alternatives, if the URL route ever disappears

- **Draw in the app.** `SessionMode` (the footer's mode-label slot) and `AbovePrompt` render on the desktop [docs §1.4]; the mod already supports `/ctxbar footer` and `/ctxbar top`. No mapping at all. Costs: the look (a run of `━` glyphs in the mode-label slot, or a band row of its own), the band hidden while the next-step box is shown (#102249), and `$.ui.status` lines not drawn in the desktop (lrdub README) [prec §1].
- **Hybrid.** The mod renders the figures as dim text in `SessionMode`; the overlay reads that Text element through UI Automation (a Name the project controls) and paints the gradient from it. Removes the store and the title, keeps the look; needs one dump to confirm the slot's Text is exposed with its text as Name (check C2). Second choice after the URL key, which needs no in-app drawing.
